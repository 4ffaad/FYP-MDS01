- (decision) Use pose-only processing as the first implementation profile; retain normalized keypoints, confidence, relative timestamps, and safe action summaries rather than patient video.
- (decision) Attach video assets to an existing EEG session as a separate child resource so the EEG pipeline and H5 model contract remain unchanged.
- (decision) Reuse the encrypted upload-draft boundary, session-scoped private storage, repository/service layering, BackgroundTasks processing, safe serialization, and cleanup policy.
- (decision) Make MediaPipe Pose Landmarker the first adapter implementation; keep computer-vision dependencies behind a VideoInferenceAdapter so MMPose or a later learned model can be evaluated without changing the API or storage contract.
- (decision) Treat pose output as sensitive research data and risk reduction, not as anonymous data; no public endpoint returns raw video, raw paths, patient references, or the full pose artifact by default.
- (decision) Defer face-redacted review video, learned spatio-temporal anonymization, video/EEG synchronization, and clinical action labels until their requirements and evaluation gates are approved.
- (capability) CAP-1: A user can stage a supported video and attach it to an existing session with an explicit privacy profile; success is an opaque draft flow, bounded validation, a 202 processing response, and no plaintext upload outside private storage.
- (capability) CAP-2: The system can process the default pose-only profile into a versioned normalized pose artifact and analysis summary; success is a fixture completing with relative timestamps, keypoints, confidence values, quality flags, and no retained audio, subtitle, metadata, or pixel frames.
- (capability) CAP-3: A user can inspect video processing status and safe research results in a dedicated frontend area; success is a UI/API demonstration showing opaque IDs, status, privacy profile, duration/frame summary, and non-clinical action-analysis output without private paths or source media.
- (capability) CAP-4: The system can fail closed when video validation or privacy processing is incomplete; success is that decode failures, unsupported media, non-monotonic timestamps, missing required pose coverage, and unsupported multi-person input produce bounded safe errors and do not publish a derivative.
- (capability) CAP-5: The project can evaluate transformed-video utility and residual privacy risk before making a stronger release claim; success is a reproducible research report covering action utility when labels exist, re-identification, sensitive-attribute inference, cross-clip linkage, temporal coverage, and non-video leakage checks.
- (constraint) Raw video, decrypted frames, audio, subtitle/data streams, original metadata, and transient processing files remain private and are deleted after processing according to the configured retention policy.
- (constraint) Public API responses expose only generated identifiers, safe technical metadata, processing state, research-only summaries, and bounded error text; they never expose patient references, original filenames, filesystem paths, source media, cryptographic hashes, or unreviewed clinical interpretations.
- (constraint) Video routes remain thin; database access belongs in repositories, processing belongs in video services, and long-running work is scheduled through FastAPI BackgroundTasks.
- (constraint) The first runtime must not invent an action model, clinical output contract, privacy guarantee, or numerical acceptance threshold. Any development stub is clearly labeled research/development data.
- (constraint) Video processing is a separate adapter and dependency boundary; it must not change the reviewed EEG input contract or couple computer-vision packages to the H5 runtime.
- (assumption) The first release attaches one video asset to an existing session and assumes one primary patient is visible; additional people are detected or flagged and never silently ignored.
- (assumption) Audio is not needed for the first movement-analysis use case and is removed unconditionally from derived processing inputs.
- (assumption) The initial fixture set is synthetic or consented research data and does not justify production privacy or clinical claims.
- (question) Which movement actions or clinical events must the analyzer recognize, and what labeled fixture set will define utility?
- (question) Is human visual review required? If yes, what review-only redacted-video retention window and face/multi-person coverage policy are acceptable?
- (question) What video containers, codecs, duration, resolution, frame-rate, and upload-size limits should be approved?
- (question) Must video and EEG be time-aligned, and what recording-relative representation is safe to expose?
- (question) Which release audience and attacker model define the privacy gate, and who approves the thresholds for re-identification and sensitive-attribute leakage?
- (question) Should encrypted pose artifacts be retained for research, or should the first release retain only aggregate action summaries after processing?

- (decision) One job may select one or more privacy profiles and produce separate output artifacts from the same validated source; profiles must not be chained implicitly.
- (decision) The initial profile registry contains pose-only and face-redacted; shared stream/metadata scrubbing is mandatory preflight, not a separate user-facing profile.
- (decision) Pose extraction and face detection are privacy transforms only. Their outputs are not action predictions, clinical labels, confidence scores, or model results.
- (decision) Implement a VideoPrivacyPipeline protocol and registry with common validation, output inspection, encryption, retention, and cleanup around profile-specific transforms.
